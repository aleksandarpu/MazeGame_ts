# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Browser-based, turn-based multiplayer maze quiz game written in TypeScript with no UI framework (plain DOM + `<canvas>`). Players roll a die, move through a braided maze from the bottom-left start `(0, height-1)` to the top-right finish `(width-1, 0)`, and landing on a flag triggers a timed multiple-choice question. Question content (in `assets/data/*.json`) is Serbian Cyrillic.

## Commands

- `npm run dev` — Vite dev server with HMR; `index.html` loads `/src/index.ts` directly.
- `npm run build` — `tsc` (type-check only, `noEmit`) then `vite build` → bundled output in `dist/` (`dist/index.html` + hashed files in `dist/assets/`).
- `npm run preview` — serve the built `dist/` locally.
- `npx tsc` — type-check only.
- Deploy: `.github/workflows/deploy.yml` builds and publishes `dist/` to GitHub Pages on every push to `main` (repo Settings → Pages → Source must be "GitHub Actions"). `vite.config.ts` sets `base: "./"` so the build works under `/<repo>/`; keep asset references in `index.html` relative (e.g. `./favicon.ico`) so Vite bundles them. Serving the repo root directly can't work: `index.html` loads `/src/index.ts`, which browsers can't run.
- `node server.js` — old minimal HTTP server on port 3000 that returns `index.html` for every request; it doesn't serve JS or other files, so use `npm run preview` instead.

There is no test runner or linter configured.

**Question editor** — `tools/question-editor/question_editor.py` is a separate Python 3 / Tkinter desktop app (no dependencies) for editing `assets/data/*.json`: `python tools/question-editor/question_editor.py [file]`. On the left it lists each question with its answers; on the right it edits the selected one. It can create a new file, add and delete questions, add, delete and reorder answers, and edit the group name. It won't save a file without a group name or without questions. It keeps the files' formatting (4-space indent, raw UTF-8, CRLF), so an unedited save is byte-identical. It relies on the same convention as the game: the first answer is the correct one. See its README.

## Architecture

**Entry / router — `src/index.ts`.** Holds a small global `appState` and a chain of `navigateTo*` functions: Login → Lobby → Game Room → Game Play. Each screen module exports a `render*Screen(container, ...data, ...callbacks)` function that wipes `#app-container` (including `removeAttribute("style")`, because the screens share that element and a leftover `alignItems: center` from the login would shift later screens) and builds its DOM, with inline styles or, for the game room and game screens, an injected `<style>` (`rs-*` / `gs-*` classes); navigation happens through the callbacks. `renderLobbyScreen` returns a function that redraws only the room list. Each controller stores its Firestore unsubscribe (or the game cleanup) in `stopCurrentScreen`, which the next `navigateTo*` calls first.

**Game state is a single mutable object** (`GameState` in `src/GameState.ts`: `maze`, `players`, `width`, plus `phase` (roll / move / question / finished), `rollCount`, `lastRoll`, `answerCount`, `lastAnswerCorrect`, `winnerId`). `navigateToGamePlay()` builds it from the Firestore game doc, and `game.ts` mutates it. Exactly one player has `isCurrentTurn`; `steps` is the remaining moves for that turn.

**Game loop — `src/game.ts` (`renderGamePlayScreen`)** wires everything together:
1. `dice-pop-up.ts` (`showDiceRollPopup`) shows a 3D physics die (`DiceScene` class, math in `dice_math.ts`, ported from `playful_dice_roller (3).html`). The player clicks it or presses Space. The rolled value becomes `currentPlayer.steps` (1–6). Other clients see `showSpectatorDicePopup`, which can't be clicked: it tumbles when the roll starts (`rollCount` +1) and, once settled, fades to the real `lastRoll` face.
2. `maze_input_controller.ts` listens for arrow keys / canvas clicks, validates adjacency against `cell.walls`, and calls back with a target cell.
3. `player_move.ts` (`executePlayerMove`) decrements steps, checks victory, checks `cell.flag` (suspends the turn and opens a question), or advances the turn when steps hit 0.
4. Question outcome: correct → +2 score, +3 steps, turn continues; wrong/timeout → steps = 0, next player. This logic lives inline in `game.ts`; `question_resolver.ts` is a duplicate, currently unused version of it.
5. `render_maze.ts` (`renderGame(ctx, maze, players, cellSize, board, time)`) draws the whole maze. `game.ts` calls it every frame from a `requestAnimationFrame` loop; `time` drives the twinkling crown (`crown21`/`crown22` alternate), the pulsing finish glow and the current player's bob. Flags use `assets/images/question_{typeId}.png` and players `player{spriteId}.png`, scaled to fit the cell with their proportions kept. Until the images load, colored squares and circles are drawn instead. The scoreboard and current-player box are re-rendered via `innerHTML` in `updateUI()`.

**Multiplayer turns.** Only the client whose turn it is acts: it gets input, the real dice and the question. A mock player's turn is played by the first real player (`controllerOf`). Every local change goes through `commit()` → `publish()`, which saves `syncedPart(gameState)`. `renderGamePlayScreen` returns `{ cleanup, applyRemote, removePlayers }`. `applyRemote` takes the saved state and replays what changed compared to the local state: the turn changing opens a dice pop-up, a position change plays a footstep, `rollCount`/`lastRoll` drive the spectator dice, `answerCount` shows the result pop-up, and `finished` shows the victory pop-up. Our own saves come back identical, so nothing is replayed, and snapshots with pending writes are skipped. `removePlayers` is called by one client (the first real player still in the room) for players who left the room, and passes the turn on if it was theirs. Call `cleanup` when leaving the game screen.

**Themes** — `themes.ts` defines three style sets for the game screen: `garden` (Garden Board, the default), `neon` (Neon Night) and `candy` (Candy Pop). Each has CSS scoped under `.theme-<id>` plus a `board` color set used by the canvas renderer. `game.ts` holds the layout CSS every theme shares (`.gs-*` classes, desktop grid / stacked at <= 1024px) and puts `gs-root theme-<id>` on the screen root. The color dots in the scoreboard header switch the theme; the choice is saved in `localStorage` (`mazegame.theme`). The fonts (Fredoka, Baloo 2, Lilita One) load from Google Fonts in `index.html`. To add a theme, add an entry to `themes` and its name as `theme.<id>` in every language file.

**Languages** — All UI text is in `assets/lang/<id>.json` (`en`, `sr` in Serbian Cyrillic): a flat map from key to text, with `{placeholders}`. `i18n.ts` has `t(key, params)` and `tPlural(key, count)`. `tPlural` picks `<key>.one` / `.few` / `.other`, following `Intl.PluralRules`, and passes the count as `{n}`. Keys are typed from `en.json`, and `sr satisfies Record<TextKey, string>` makes `npx tsc` fail if a language is missing a key. Every screen has a language picker (`createLanguagePicker(onChange)`) and redraws itself when the language changes: the login keeps the typed name, the lobby keeps its room list, and the game rebuilds the mute row and runs `updateUI`. Pop-ups use the language that is active when they open. The choice is saved in `localStorage` (`mazegame.language`); the default is `sr` if the browser language is Serbian, otherwise `en`. To add a language, add a JSON file with the same keys, an entry in `languages` and a `satisfies` line. Never hard-code UI text: add a key. Question content (`assets/data`) isn't translated.

**Maze** — `maze_generator.ts` builds a grid via recursive-backtracker DFS starting at the start cell, then "braids" it by knocking out one wall of every dead end (so there are loops). `place_flags_in_maze.ts` attaches `Flag { typeId }` objects directly onto cells (4 types × N each), excluding start and finish.

**Questions.**
- `question-pop-up.ts`: `pickQuestion(flagTypeId)` picks a random question and shuffles its answers into an `ActiveQuestion` (`{ flagTypeId, ordNum, answerOrder, timeLimit }`). It is saved in the game state (`question`), so every player sees the same question in the same order. `createQuestionPopup(container, active, onAnswer?)` shows it. With `onAnswer` (the answering player's client) the question can be answered by click or keys 1–4, and `onAnswer` gets the original answer index, or null on timeout. Without it the pop-up is read-only (other players) and closes when `question` becomes null. `appendFormattedText` builds text from DOM text nodes, never `innerHTML`: `\n` becomes `<br>`, and text between a pair of `*` is shown in red (a line with an unpaired `*` is shown as-is). Answer index 0 in the data is the correct one (`CORRECT_ANSWER_INDEX`).
- `answer-pop-up.ts` `showResultPopup(container, isCorrect, onDismiss, { answerText, playerName? })` shows the chosen answer in green or red ("Time's up" when `answerText` is null). With `playerName`, the message names the player (someone else's answer).
- `questions.ts` imports the four `assets/data/*.json` files statically (Vite bundles them; `resolveJsonModule` is on). File format: `{ Group, Questions: [{ Question, Answers }] }`. Flag `typeId` maps to files as 1 `gramatika`, 2 `jezik`, 3 `pravopis`, 4 `sluzba`. `getRandomQuestion(typeId)` returns `{ ordNum, group, questionText, answers }`. It strips stray U+FEFF characters and normalizes line endings. `questionText` contains `\n` line breaks, so display it with `textContent` + `white-space: pre-line`, not `innerHTML`. `assets/images/question_{1..4}.png` are the matching flag icons.
- Reaching the finish calls `index.ts`'s `showVictoryPopup`, which removes the game's input listeners and shows `victory-pop-up.ts` (its button goes back to the lobby).

**Sounds** — `sounds.ts` preloads `assets/sound/*.wav`; `playSound(name)` plays a copy each time, so sounds can overlap. Players can mute groups of sounds from the "Mute:" row above the maze. The groups are listed in `muteGroups` (steps, dice, answers, next player, wall; their names are `mute.<id>` in the language files), and the choice is saved in `localStorage` (`mazegame.mutedSounds`). A muted `playSound` still returns an (unplayed) element. `winning` is not in any group, so it always plays. Triggers: roll (while the die tumbles in `dice-pop-up.ts`; faded out with `fadeOutSound` when it settles), footstep (valid move), damageTaken (move blocked by a wall or the edge while the player has steps), collect / wrongAnswer (question result, including timeout), winning (inside the victory pop-up), changePlayer (in `game.ts`'s `handleTurnAdvance`, which waits `TURN_CHANGE_DELAY_MS` before the next player's dice).

**Firebase** — `firebase_init.ts` initializes Firestore and the Realtime Database.
- `presence.ts` (RTDB `status/{userId}` = `{ name, state, roomId, lastChanged }`): the user id is new on every page load (not in `sessionStorage`, which "Duplicate tab" copies), so each tab is its own player. `startPresence` runs on login and registers `onDisconnect` → offline on every reconnect. `setPresenceRoom` records the room the user is in.
- `rooms.ts` (Firestore `gameRooms/{roomId}` = `{ name, status: waiting|started, hostId, isMock?, players: { [userId]: { name, status, joinedAt, isMock? } } }`): join, leave, ready and start are transactions, with at most 6 players per room. When the last real player leaves, the room is deleted. Mock rooms (`mock_alpha`, `mock_beta`, seeded on login, with fake players that are always ready) are reset to their seed instead. A closed tab can't write to Firestore, so every logged-in client runs `startRoomCleanup`, which removes room players whose presence is offline or points at another room (skipping players who joined in the last 15 s). Because of that check, presence is set to the room *before* the Firestore join and cleared *after* the leave.
- The room screen ignores a cached snapshot that doesn't list the user: transactions aren't applied to the local cache, so right after `joinRoom` the cached room is stale.
- `games.ts` (Firestore `gameRooms/{roomId}/game/state` = `{ gameId, width, maze (JSON string, since Firestore has no nested arrays), players, phase, rollCount, lastRoll, answerCount, lastAnswerCorrect, winnerId }`): `startRoomIfAllReady` creates it in the same transaction that sets the room's `status: started` and `gameId`, with players in join order. Clients ignore a game doc whose `gameId` doesn't match the room's (a cached earlier game). Deleting or resetting a room deletes its game doc too (Firestore doesn't delete subcollections).

## Quirks

- Vite is the only bundler; TypeScript never emits files. Import static files from `assets/` through ES imports (e.g. `import url from "../assets/images/player1.png"`, or import the JSON directly) so Vite fingerprints them and includes them in the build. Plain string paths to `assets/` won't be copied into `dist/`.
- `playful_dice_roller (3).html` and `test_question_pop-up.html` are standalone UI prototypes, not part of the app (the dice one has been ported to `src/dice-pop-up.ts`).
